# Обнаружение мошеннических схем

## Назначение

Текущая реализация обнаружения находится в `events/fraud_detection.py`. Один и тот же модуль используется командой Django `analyze_fraud` и задачей Celery Replay (`api.replay_events`).

На данный момент реализован детерминированный Rule-based анализ событий, сохранённых в PostgreSQL (`events_eventlog`). ML, GNN, Graph Mining и вычисление откалиброванного risk score в текущем коде не реализованы.

## Входные данные

Детектор получает список объектов `EventLog`, отсортированный по `event_time`, затем по `seq`. Для каждого события используются:

- `event_id` — идентификатор события;
- `event_type` — тип события;
- `event_time` — время события;
- `client_id` — клиент-инициатор;
- `account_id` — исходный счёт;
- `payload` — дополнительные поля, в частности `device_id` и `target_account_id`.

`amount` и IP-адрес не участвуют в текущих правилах обнаружения.

## Реализованные правила

### 1. Shared Device

Файл: `events/fraud_detection.py`, функция `detect_candidates()`.

1. События группируются по `payload.device_id`.
2. Для каждого устройства собирается множество уникальных `client_id`.
3. Устройство становится кандидатом на инцидент, если с него зафиксирована активность **трёх или более разных клиентов**.

В связанные данные кандидата включаются события, в payload которых присутствует соответствующий `device_id`, их клиенты и счета.

Важно: правило считает клиентов по всем типам событий, а не только по событиям входа (`login`).

### 2. Fast Chain

Правило рассматривает последовательность трёх переводов между счетами:

`Account A → Account B → Account C → Account D`

Условия текущей реализации:

- `event_type == "transfer"`;
- `first.payload.target_account_id == second.account_id`;
- `second.payload.target_account_id == third.account_id`;
- каждый следующий перевод происходит строго позже предыдущего;
- интервал между первым и вторым, а также между вторым и третьим переводами не превышает 2 секунд.

Если третий перевод не замыкает путь на клиента-инициатора первого перевода, кандидат классифицируется как `fast_chain`.

### 3. Cycle Transfer

Используется тот же поиск трёх последовательных переводов. Если счёт-получатель третьего перевода сопоставлен с клиентом, который инициировал первый перевод, кандидат классифицируется как `cycle_transfer`.

Иными словами, проверяется клиентский цикл `A → B → C → A`.

### Как сопоставляется счёт и клиент

В текущем коде строится словарь `account_to_client` из событий: для каждого `account_id` сохраняется `client_id` последнего события в переданном списке. Это сопоставление используется для определения участников цепочек и проверки замыкания цикла.

## Сохранение результатов

Найденные кандидаты преобразуются в записи `api.FraudAlert`.

- `fingerprint` — SHA-256 от типа схемы, идентификаторов событий (для переводов) и набора связанных клиентских/устройственных идентификаторов.
- `alert_id` — `AL-` плюс первые 12 символов fingerprint в верхнем регистре.
- Повторные кандидаты с одинаковым fingerprint внутри одного запуска дедуплицируются.
- Сохранение выполняется через `update_or_create()` по `fingerprint`.
- При обновлении меняются идентификатор/схема/описание/признаки/участники/ссылки на граф. Статус аналитика и `risk_score` в defaults не входят и таким обновлением не сбрасываются.
- `risk_score` остаётся `NULL`: калиброванная формула оценки риска пока не реализована.

## Запуск

Полный анализ журнала событий:

```bash
python manage.py analyze_fraud
```

Повторный анализ временного интервала выполняется Celery-задачей Replay через API. В детектор передаются `start_time` и `end_time`; обе границы фильтрации включительные (`gte` и `lte`).

## Ограничения текущей реализации

- Детектор загружает выбранные события целиком в память (`list(queryset)`).
- Поиск цепочек реализован вложенными циклами по списку переводов (до трёх уровней). При росте числа переводов время анализа может быстро увеличиваться; алгоритм не следует считать оптимизированным для больших потоков.
- Replay анализирует только события внутри выбранного интервала. Контекст до и после интервала не добавляется, поэтому цепочка, пересекающая границу интервала, может быть пропущена.
- Проверка Fast Chain/Cycle использует соответствие `account_id → client_id`, полученное из событий; отдельной проверки актуального владельца счёта в Neo4j нет.
- Правила являются эвристическими признаками подозрительной активности, а не доказательством мошенничества.
- В текущих правилах не используются сумма перевода, частота за длительный период, IP, PageRank, community detection или ML/GNN.

## Идеи для дальнейшей работы

Перед увеличением объёмов данных стоит профилировать детектор и заменить полный перебор цепочек на индексированный поиск по исходному/целевому счёту и времени. Новые правила и ML-компоненты следует документировать отдельно от реализованной логики, явно помечая их как планируемые.
